\section{Architecture and RMI distribution}
\subsection{Component boundaries}
The system has five roles: a console client, middleware, and three resource managers
for flights, cars, and rooms. Both implementations use this topology:
\begin{center}
\begin{tabular}{ccc}
 & & Flights manager\\
Console client $\longrightarrow$ & Middleware $\longrightarrow$ & Cars manager\\
 & & Rooms manager
\end{tabular}
\end{center}
Each manager owns its inventory, availability, prices, and backend booking records.
Middleware routes inventory operations and owns customer accounts, reservation ledgers,
billing, bundles, and customer deletion. Central customer ownership avoids customer
replication and lets one service construct a bill spanning all three resource types.
It also makes middleware a single point of failure; availability after crashes is outside
the implemented scope.

The client-facing \code{IResourceManager} contract retains all 21 original method
signatures. An internal \code{IInventoryManager} extends it with
\code{reserveInventory(key, quantity, bookingId)} and \code{releaseInventory(bookingId)}.
A successful acquisition returns an immutable receipt containing the item key, quantity,
and booked price. Middleware never creates customers at the inventory managers. The
legacy customer methods remain available there for starter compatibility.

\subsection{RMI communication and compatibility}
The RMI client resolves middleware in a registry and invokes the existing interface.
Middleware resolves three independent manager stubs and forwards each resource operation
to its owner. Shared registry/export lifecycle code handles bindings and shutdown;
hostnames, registry ports, binding prefixes, and exported object ports are configurable.
The console dispatcher is reused. Small starter repairs remove an illegal source character,
add a bill total, and accept the documented bundle flags. Optional registry/prefix properties
support deployment without changing the client-facing contract.

The final working tree shares its asynchronous business core between transports:
\code{AsyncMiddleware} contains customer coordination, while the RMI \code{Middleware}
facade supplies synchronous interface methods. RMI backend calls run through an executor
adapter; TCP endpoints use asynchronous socket channels directly. Resource managers share
the same transport-independent inventory implementation.

\section{TCP message passing and general wrapping}
\subsection{A reusable invocation service}
Both client--middleware and middleware--manager links use persistent TCP sockets.
\code{TcpChannel.invoke(Method, Object[])} is the general asynchronous invocation service.
\code{Services.blocking(IResourceManager.class, channel)} creates a proxy exposing the
entire client interface. The console calls ordinary methods on this proxy and waits for
each result before issuing its next command. The proxy handles every operation, including
both \code{newCustomer} overloads, without operation-specific message layouts.

The same \code{Protocol.write} and \code{Protocol.read} services create and parse messages
on both links. Method signatures are derived from the interface rather than supplied
as arbitrary reflective targets. \code{Operations} validates the operation, argument
count, and argument types; middleware accepts client methods, while inventory endpoints
also accept the internal acquisition/release operations. The Java interface still declares
\code{RemoteException} for compatibility, but TCP communication uses no RMI calls or Java
object deserialization.

\subsection{Framing and data representation}
\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}lX@{}}
\toprule
Envelope & Fields in transmission order\\
\midrule
Common prefix & Four-byte payload length; protocol version; message kind; request ID\\
Request payload & Operation signature; argument count; typed argument values\\
Response payload & Nullable error string; typed result value\\
\bottomrule
\end{tabularx}
\end{center}
Integers, booleans, nulls, UTF-8 strings, string vectors, and reservation receipts have
explicit type tags. Strings carry byte lengths, so locations and multiline bills do not
require delimiter escaping. Length framing is necessary because TCP is a byte stream:
one message may arrive in fragments, or several messages may arrive together. Reading
the exact declared payload isolates each message in either case.

The decoder rejects unsupported versions, invalid kinds/type tags, negative or excessive
lengths, and trailing frame bytes. A frame is limited to 1 MiB, an argument list to
32 entries, and a string vector to 10000 entries. These limits bound individual incoming
messages. Unknown signatures produce error replies rather than arbitrary method execution.

\subsection{Correlation, timeout, and failure semantics}
Each channel assigns a monotonically increasing request ID and stores a future in a
pending-request map. A dedicated writer serializes queued frames; a dedicated reader
looks up response IDs and completes the corresponding futures. Responses can therefore
arrive out of order without being delivered to the wrong caller. Completed requests
cancel their timeout tasks.

The default channel timeout is 30000 ms and is configurable. A timeout or disconnect
closes that channel and fails its pending requests. There is no automatic reconnect or
automatic mutation retry: if a connection fails after a server changed its state, the
caller cannot infer whether the mutation occurred. Backend booking tokens support
idempotent cleanup while the same backend remains alive, but do not guarantee end-to-end
exactly-once client commands. A multi-resource operation can involve several reply waits;
the channel timeout is not a deadline for the whole bundle.

\section{Concurrency, customers, and bundles}
\subsection{Progress without waiting for backend replies}
\code{TcpServer} separates accepting connections, reading requests, and writing responses.
For middleware, request dispatch returns a completion stage immediately. A completion
callback enqueues the response when its backend work finishes; no middleware dispatcher
calls \code{get()} or \code{join()} on a backend future. Dedicated socket threads can wait
for bytes or queued output, but such waits do not occupy a shared request worker awaiting
an inventory result. This is asynchronous coordination using blocking socket I/O, rather
than a claim that all sockets use nonblocking NIO.

Each customer has an ordered chain of futures. Reserving, querying the bill, and deleting
that customer execute in sequence, preserving ledger consistency. The short account
monitor protects queue updates and is not held while waiting for a network reply.
Different customers and independent inventory queries can progress while one customer's
reservation is delayed. Customer IDs are generated with collision checking against
existing accounts.

Inventory endpoints accept multiple connections and dispatch operations onto four
execution workers with a bounded queue. Complete inventory transitions are synchronized
inside \code{ResourceManager}; two callers cannot both obtain the last available seat.
This briefly serializes state mutation at one manager, while connection handling and
request execution remain concurrent. Inventory locks never wait for another server.

There are 64 accepted connections per server, 1024 pending requests per channel/session
or customer queue, and 256 queued inventory tasks. Overload is rejected or closes the
affected connection. These bounds control outstanding work; they are not throughput
measurements, and long-lived customer/token records can still accumulate in memory.

\subsection{Reservation and deletion invariants}
Every backend acquisition has a unique booking ID. Successful replay returns the same
receipt, and repeated release does not restore inventory twice. Cancellation tombstones
also prevent a delayed reserve from succeeding after its release arrived first. Middleware
stores the booking token and receipt in the customer ledger only after successful
coordination. Billing combines all resource types and uses a long total with deterministic
item ordering. It preserves the starter's grouped latest-price convention: a later booking
of an item can reprice that customer's existing grouped reservations of the same item.

Deletion releases each confirmed booking and removes it from the ledger only after
confirmation. If deletion is interrupted, confirmed releases are not repeated; the
remaining work is retained. New bookings and bill queries are rejected during incomplete
deletion, and a later deletion request can resume while the relevant endpoints are usable.

\subsection{Bundle coordination and its limits}
Middleware validates flight inputs, aggregates duplicate flight numbers into quantities,
and adds the optional destination car and room. Acquisitions run in a future chain.
The customer's ledger is updated only when all acquisitions succeed. If an item is
unavailable, middleware cancels this attempt's tokens while preserving earlier reservations.
Attempted tokens are recorded before sending acquisitions, allowing cleanup even if an
error follows a backend mutation. Unconfirmed cancellations remain pending for later retry.

This compensation strategy handles ordinary availability failures and retryable remote
errors; it is not a crash-safe distributed transaction. Queries may observe intermediate
acquisitions. All inventory, customers, booking records, and tombstones are in memory.
A closed TCP backend channel requires operational recovery, and component restart does
not restore prior state. Persistence, replication, and automatic reconnection are not
implemented.
